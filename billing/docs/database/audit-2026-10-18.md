# Database audit 1 — 2026-10-18

Whole-database review of `develop` at `eb32e7c` (includes Nepal payments, #26): every migration under
`database/migrations` and `app/Modules/*/Database/Migrations`, the models, and the query-heavy code
(automation tasks, dashboards, list pages, search, billing and payment paths). Fixes are on
`feature/db-hardening`; larger items are GitHub issues:

- #47 DB: production install path for reference data and the first administrator (blocking for go-live)
- #48 DB: trigram indexes for contains search on PostgreSQL
- #49 DB: retention for unpruned tables, and no count(*) on log pages
- #50 DB: CHECK constraints for money, stock and status invariants on PostgreSQL
- #51 DB: support Awaiting reply queue sorts by per-ticket subqueries
- #52 DB: integrity check for cross-module ids without foreign keys

## How the evidence was gathered

- **PostgreSQL 18.6** (`postgres:18.6-alpine`, private container) migrated and seeded with the demo seeders,
  then loaded with synthetic data through `generate_series`: 100k clients, 100k client logins, 50k contacts,
  300k invoices, 900k invoice lines, 343k transactions, 200k credit-ledger rows, 300k gateway-log rows,
  200k payment attempts, 100k orders, 200k order items, 150k services, 50k addons, 1.0M usage snapshots,
  300k module-log rows, 80k domains, 240k registrar-log rows, 100k tickets, 500k ticket messages, 300k ticket
  events, 1.0M activity-log rows and 25k automation runs (1.3 GB).
- **EXPLAIN (ANALYZE)** on 29 probes taken from the code, before and after the fixes (table below).
- **Queries per page:** 32 admin pages rendered through the HTTP kernel as the seeded administrator against
  that database, counting every query and flagging repeats and statements over 40 ms.
- **Tests:** a failing test first for every behaviour change, then the full suite on SQLite and PostgreSQL.

The machine was shared with four other agents (load 5–8 on 4 vCPUs), so absolute times are noisy; the plan
shapes and the before/after ratios are the evidence.

## Cross-cutting

### Indexes

- PostgreSQL does not index foreign keys. 47 foreign keys had no index whose leading column covers them; this PR
  adds them, plus seven non-FK indexes (sign-up date, transaction sort, three `lower(email)` expressions, two
  partial uniques): 54 in all, in seven migrations. Checked against `pg_constraint`/`pg_index` afterwards: the
  only foreign key without an index is `themes.created_by` (a handful of rows).
- New helper `App\Modules\Core\Support\OnlineIndex`: builds and drops indexes CONCURRENTLY on PostgreSQL
  (migration sets `$withinTransaction = false`), uses IF NOT EXISTS, rebuilds an INVALID leftover from an
  interrupted build, and keeps Laravel's default index names so a later `dropIndex([...])` still works. Use it
  for every index on a table that can be large.
- Partial unique indexes enforce rules that NULLs or booleans defeat (`currencies_single_default_unique`,
  `tld_prices_default_price_unique`). Both are portable to SQLite.
- Redundant indexes removed: three on `support_tickets`.
- `%term%` search cannot use a btree on either database. PostgreSQL needs `pg_trgm` GIN indexes on the
  searched expressions: #48.

### Concurrency

- Money paths are sound: invoice rows are locked by every payment, credit, capture, refund and chargeback
  action; the credit ledger serializes on the client row; document numbers lock their sequence row; promotion
  usage and stock are conditional atomic updates; idempotency keys and provider ids are unique.
- Offset paging over rows the loop itself changes (`->each()` = LIMIT/OFFSET) skipped work in seven
  automation loops. Use `eachById()`/`chunkById()`/`lazyById()` whenever the callback writes. Fixed.
- One lock-order inversion (client merge vs credit ledger), low risk; noted above.

### Portability (SQLite and PostgreSQL)

- `whereDate()` on a **timestamp** column compiles to `col::date` on PostgreSQL and `strftime()` on SQLite;
  neither can use an index. Use a half-open range (`>= start of day`, `< start of next day`). Fixed in the
  order and transaction lists and the usage sync. On **date** columns `whereDate()` is harmless on PostgreSQL.
- `Like::where()` (`lower(col) like ? escape '!'`) and `whereLike()` (`ilike` on PostgreSQL) behave the same
  on both databases.
- Global search providers for clients and services use `limit(5)` without `orderBy`, so results can differ
  between databases and runs (rule 4). Low; left for the module owners (the providers are being edited in #41).
- Timestamps are `timestamp without time zone` on PostgreSQL. This is consistent while `APP_TIMEZONE` stays UTC
  and every bucketing happens in PHP; changing the app time zone later would silently shift stored values.
  Dashboard day/week buckets are UTC days, not the business time zone (forwarded to #41).

### Migration safety

- The new migrations add indexes CONCURRENTLY, are idempotent, and are reversible; rollback and re-apply were
  run on the populated PostgreSQL database.
- Existing backfills: `100300` (driver config encryption) is chunked and reversible: the model. `600400`,
  `900200` and the currency PR's updates are single statements over small tables: acceptable now, but new
  backfills on large tables must be chunked.
- Data-dependent constraints (`currencies` single default, `tld_prices` default price) stop the migration with
  an actionable message instead of deleting data.

### Growth

At 100k clients the largest tables in this test were `service_usage_snapshots` and `activity_log` (1M rows
each), `invoice_items` (900k) and `support_ticket_messages` (500k); the database was 1.3 GB. With the indexes in
this PR every list page, client page and automation lookup stays index-bound; the remaining linear costs are
`%term%` search, paginator `count(*)` on log tables, the awaiting-reply queue order and the dashboard
aggregates.
