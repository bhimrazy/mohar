Read the release's upgrade notes first. Then take a database backup: a database change cannot always be undone.
See [Backups](../backups/).

<Tabs syncKey="install">
<TabItem label="Docker Compose">

<Steps>

1. Check **Setup → Automation**: if the daily run or a **Run now** is in progress, wait for it to finish. Then back
   up the database.

2. Get the new release into the install folder (for example check out its tag), then deploy it.

    ```bash
    deploy/bin/deploy
    ```

    To deploy an image you pushed to a registry instead of building on the host:
    `deploy/bin/deploy --image ghcr.io/<owner>/<repo>@sha256:<digest>`.

</Steps>

### What the deploy does (blue-green)

The stack runs two copies of the app, *blue* and *green*; one is live. A deploy builds the new release, checks that
its database changes keep the live version working, applies them, and starts the new version beside the live one.
Only when the new version passes its health check does the web server switch traffic to it, without a gap. Then the
background workers move over: each finishes its current job first. The scheduler and the automation worker move
last, and while an automation run is in progress the deploy waits for it, up to an hour. The previous version keeps
running, ready for a rollback.

If the new version does not become healthy, the deploy stops it and traffic stays where it was. To see which copy is
live: `deploy/bin/deploy status`.

**Rolling back:**

```bash
deploy/bin/deploy rollback   # back to the previous version, which is still running; run it again to roll forward
deploy/bin/deploy retire     # once you are sure: stop the previous version to free its memory
```

Database changes are not reversed, and do not need to be: each release's changes keep the previous release working.
If a release broke that rule, restore the backup you took in step 1.

</TabItem>
<TabItem label="Without Docker">

<Steps>

1. Put the site in maintenance mode and back up the database.

    ```bash
    php artisan down
    ```

2. Deploy the new release, then install and build:

    ```bash
    composer install --no-dev --optimize-autoloader
    npm ci && npm run build
    ```

3. Apply the changes and refresh the caches:

    ```bash
    php artisan optimize:clear
    php artisan migrate --force
    php artisan app:install --no-interaction
    php artisan optimize
    php artisan queue:restart
    ```

4. Bring the site back.

    ```bash
    php artisan up
    ```

</Steps>

</TabItem>

## What the installer changes on an upgrade

Running `app:install` again is safe. It adds reference data the release introduces and resets the permissions of the
four built-in roles (Full Administrator, Billing, Support and Sales) so new permissions reach them. Each reset is in
the activity log. Custom roles, and the names you gave built-in roles, are kept.

<Aside>
	If you changed a built-in role's permissions, the upgrade resets them. Copy the role into a custom role to keep
	your own permissions.
</Aside>

Email templates you never edited move to the new wording. Templates you edited keep your text, and the template
editor shows **New default available** with a side-by-side comparison.
