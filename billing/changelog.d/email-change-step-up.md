### Security

- **Changing the sign-in email needs a recent password confirmation, and the old address is told (#388).** Before, Settings → Profile changed the email with no step-up, so a hijacked session could move the account to an address the attacker controls, verify it and reset the password there. Saving a new email now asks for the password first (the same confirm dialog and 15-minute window as other sensitive actions; JSON clients get 423). A name-only save is unchanged. A login without a password can't change its email until it sets a password (the profile page says so; JSON gets 423 with `code: password_not_set`). After a change the old address gets "Your sign-in email was changed" with the new address partly masked (`a***w@example.com`), the change is written to the activity log (`auth.email_changed`), and the new address is unverified and gets a verification link. If the template system refuses or suppresses that notice, the person sees a warning and the activity log records `auth.email_change_notice_failed`; nothing else sends it. A login's own email change now clears verification on both paths: a staff member who changes their own email under Admin → Staff → Edit must verify the new address before returning to the admin area (before, only Settings → Profile did). Two logins taking the same address at once get the "already taken" error. Admin → Staff → Edit was already behind step-up and still mails both addresses. A 3-character local part now masks to its first character only. Upgrade notes: new always-sent email template `auth.email_changed` (run `php artisan app:install` to add it to an existing install; until then the notice goes out as a plain fallback mail). No schema or permission change.
