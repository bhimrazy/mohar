Periodic whole-application review of `develop` at `685da6f`. Baseline: `billing/docs/security/standards.md`.
Emphasis on the last two days: cPanel/WHM driver and provisioning host (#62, #65, #69, #73), notifications and

## Method

- Checked every staff route (`php artisan route:list --json`, 466 routes, 320 behind `EnsureStaff`) with a script
  that maps each one to its controller method or FormRequest `authorize()`. Then compared the permissions against
  the runtime list of sensitive permissions (`PermissionRegistry::sensitive()`) and the `password.recent` middleware.
- Listed every outbound HTTP or socket call in `app/` and traced each one to the guard it uses.
- Read the relevant code for the areas above. Wrote five throwaway Pest probes against this app, ran them on SQLite
  and PostgreSQL, then deleted them. They are not committed.
- Ran `composer audit` and `npm audit` (with and without dev dependencies).

## Blocking

### B1. The inbound email webhook secret is not a secret setting: it goes to the browser, the audit log and the database in plaintext

- **Where:** `billing/app/Modules/Support/SupportServiceProvider.php:227`. The definition is
  `new SettingDefinition('support.inbound_secret', …)` with no `secret: true`.
- **Impact:** This HMAC key is the only authentication on `POST /api/v1/inbound/email/{provider}`. Because the
  setting is not marked secret:
  - it is sent in Inertia props on Admin → Settings → Support. That page is open to anyone with
    `support.settings.manage`, which includes every seeded **Support** role through `support.*` (the permission
    is not sensitive), and to anyone with view-only `core.settings.view`;
  - it is stored in `settings.value` without `enc:v1:`;
  - it is written unmasked into the `settings.updated` audit diff;
  - changing it needs no step-up.

  Anyone who holds the key can sign inbound mail "from" any client. The mail is threaded as that client: a new
  ticket or a reply on an existing one, carrying the client's identity, which can be used for social engineering
  such as "change my account email". This breaks standards §6 (secrets are write-only, encrypted at rest, masked in
  the audit diff) and §2 (credentials are sensitive).
- **Reproduction (probes P1, P1b, both pass):** set the secret. As `actingAsStaff(['support.*'])` or
  `['core.settings.view']`, `GET /admin/settings/support` returns the value (`assertSee`). The raw `settings` row
  contains it. A `PUT` with a new value succeeds without `password.recent`, and the latest `ActivityLog` properties
  contain the new value. Signing a payload `from: victim@example.com` with the key returns 201, and the ticket's
  `client_id` is the victim's.
- **Fix:**
  1. Declare the definition with `secret: true`. Existing rows are then read as plaintext, so add a one-off
     re-encrypt step: the `Settings` encrypt command or a migration.
  2. Give the setting its own sensitive permission, for example `support.inbound.manage`, either on a separate
     section or by marking `support.settings.manage` sensitive. Wildcards then stop granting it, and the section
     requires a recent password confirmation.
  3. Add a registry-wide test: every `SettingDefinition` whose key matches `secret|token|password|key|hash` is
     `secret: true`. That test would have caught this.
  4. Rotate the secret on every install after the fix.

## Medium

### M1. Retargeting a server sends its stored WHM credentials to the new host, and the host change is not audited

- **Where:** `billing/app/Modules/Services/Http/Requests/ServerRequest.php:73` (`serverData()`: a blank
  credential keeps the stored one), `:93` (`after()`: a stored credential satisfies the check whatever the host),
  and `billing/app/Modules/Services/Actions/SaveServer.php:32-38` (only driver-setting changes are audited).
- **Impact:** Server credentials are write-only, so they cannot be read back. A staff member with
  `services.servers.manage` can still change `hostname` to a host they control and press **Test connection**. The
  stored `Authorization: whm root:<token>` (or the Basic password) is then sent there, and the change leaves no audit
  entry. The route sits behind an exact sensitive grant plus step-up, so this is an insider or stolen-session risk,
  not an external one. It does turn "write-only" into "readable by anyone who can edit the server", and it leaves no
  trace. A server with a trusted certificate pin is protected: the new host must present the pinned key, so the
  call fails closed. Servers verified against a CA chain have no such protection.
- **Reproduction (probe P2, passes):** create a cPanel server with `api_token`. `PUT` the server with
  `hostname=collector.attacker.test` and no token. The token is kept, and no `ActivityLog` row mentions the new
  host. Then `POST servers/{id}/test`, and `Http::assertSent` shows a request to `collector.attacker.test` carrying
  the stored token.
- **Fix:**
  - When `hostname`, `ip_address`, `port` or `driver` changes, require every credential the driver uses to be
    entered again. In `after()`, count a stored credential only if the destination is unchanged; otherwise clear
    the stored credentials.
  - Audit destination changes (old and new host and port) with a fixed description.
  - Add a regression test for both.

### M2. Public self-registration has no rate limit

- **Where:** `POST /register` (Fortify `Features::registration()`, `billing/config/fortify.php:117`). `limiters`
  has entries only for `login`, `two-factor` and `passkeys`. The route list shows no `ThrottleRequests` on
  `register.store`, and none on `reset-password` either.
- **Impact:** Unauthenticated scripts can create accounts without limit. Each one triggers a verification email to
  an address of the caller's choosing. That means mail amplification from the host's domain, which harms sender
  reputation, plus junk client accounts. Checkout, guest tickets, the cart and password-reset links are all
  throttled, so registration is the gap.
- **Reproduction (probe P3, passes):** 15 registrations in a row from one IP. None returns 429.
- **Fix:** Register a `register` limiter, for example 5 per hour per IP plus a global cap, and attach it to
  `register.store`, either through Fortify's `limiters` or by overriding the route. Add a modest limiter on
  `reset-password`. Pin both with a test.

## Low

### L1. Sensitive-permission routes without `password.recent`

Found by the route scan:

- `POST admin/services/server-groups`, `PUT|PATCH …/{server_group}` and `DELETE …/{server_group}` are guarded by
  `services.servers.manage` (sensitive) with no step-up (`billing/app/Modules/Services/routes/web.php:25`).
  `server_ids` moves servers between groups, which changes where new accounts are provisioned.
- `POST admin/billing/invoices/{invoice}/capture` is guarded by `billing.payments.manage` (sensitive) with no
  step-up (`billing/app/Modules/Billing/routes/web.php:38`). It captures an authorised charge. `recordPayment`
  and `markPaid` next to it do require step-up.
- `POST admin/billing/gateways/{gateway}/test` and `POST admin/billing/payment-attempts/{attempt}/check` are
  read-only towards our data and acceptable without step-up. Say so in a route comment.

**Fix:** Move the first two into `password.recent`. Add an Arch or feature test that walks `Route::getRoutes()`
and fails when a non-GET route authorises a permission for which `PermissionRegistry::isSensitive()` is true but
has no `password.recent`, with an explicit allow-list for read-only checks. Nothing pins this rule today.

### L2. Webhook delivery uses its own SSRF guard and does not bypass proxies

- **Where:** `billing/app/Modules/Notifications/Webhooks/WebhookSender.php:77-89` and `WebhookUrlGuard`.
- **Detail:** The guard itself is sound: https on port 443 in production, private, loopback and metadata ranges
  always blocked in production, DNS resolved at send time, the first address pinned with `CURLOPT_RESOLVE`, no
  redirects followed. It still has two weaknesses:
  - it does not set `proxy => ''`. If `HTTPS_PROXY` or `https_proxy` is set for the queue worker, the proxy
    resolves the name again and the pin is lost, which allows DNS rebinding;
  - it duplicates the kernel `OutboundAddressGuard` (ADR 0015), whose docblock lists webhooks as one of its
    callers.
- **Fix:** Resolve and pin through `OutboundAddressGuard::pin()`, which bypasses the proxy and uses
  `CURLOPT_CONNECT_TO`. Keep the webhook-specific rules (https only, port 443, private ranges always refused in
  production) as a stricter policy on top of it.

### L3. The client-area hosting password change is unthrottled and makes a synchronous call to the panel

- **Where:** `POST client/services/{service}/password` (`billing/app/Modules/Services/routes/web.php:58`). It
  calls `runNow` and makes a synchronous WHM call. Ownership is scoped correctly (`ServiceActionController::owned`).
- **Impact:** A logged-in client can drive repeated `passwd` calls to the shared server. The same applies, more
  mildly, to `client/payment-methods`, `client/invoices/batches` and `client/credit/add-funds`.
- **Fix:** Add `throttle:6,1` to the password route. Consider a client-area default limiter.

### L4. Registrar credentials are outside the sensitive tier (latent)

- **Where:** `billing/app/Modules/Domains/DomainsServiceProvider.php:222` and
  `billing/app/Modules/Domains/Http/Requests/RegistrarAccountRequest.php`.
- **Detail:** `domains.registrars.manage` is not sensitive and `PUT admin/domains/registrars/{registrar}` has no
  step-up. The request does not use `KeepsSecretsOutOfOldInput`, so password-type settings are flashed into the
  session when validation fails. Storage is right: `settings` is `encrypted:array` and password fields are blanked
  in props. The only driver today is `LogRegistrar`, which has no secrets, so nothing is exposed yet. The first real
  registrar would inherit all of these gaps.
- **Fix:** Before the first real registrar driver:
  - mark the permission sensitive;
  - wrap update and test in `password.recent`;
  - use `KeepsSecretsOutOfOldInput` with `settingInputPaths()`;
  - route the driver's HTTP through `OutboundAddressGuard`.

### L5. Smaller items

- The webhook signing secret is revealed once through `Inertia::flash`
  (`WebhookEndpointController.php:61,141`), so it sits in the session store until the next request. This is
  acceptable for reveal-once, but sessions must stay encrypted, or on a non-shared store, in production.
- `SaveServer.php:38` interpolates the staff-entered server name into the audit description, which goes against
  standards §4 (fixed sentences, values in properties). The text is sanitised and truncated, so it is cosmetic.
- The inbound email HMAC (`GenericDriver::verify`) covers the body only, with no timestamp. A replayed request is
  deduplicated on `message_id`, so the impact is nil today. A future provider driver should sign a timestamp too.

## Verified secure

- **Admin permission coverage:** every one of the 320 staff routes authorises in the controller or the FormRequest,
  except the deliberately open ones (dashboard, command-palette search filtered per group, own theme preference,
  own ticket signature). The "NONE" results from the scan resolve to shared helpers:
  `ModuleLogController::close()`, `SettingsCatalog::visibleSections()` and `DomainAreaRequest`. The wildcard rule
  holds in tests: `services.*` is refused on trust-certificate (`TrustCertificateTest`).
- **Step-up:** servers, trust and forget certificate, service credentials, templates, webhooks, currencies and
  rates, gateways, refunds, transactions, credit, tax, staff and roles, and the security, rates and email-delivery
  settings sections all require `password.recent`. Settings sections derive it from `isSensitive()`.
- **`OutboundAddressGuard` (#61):** probe P4 refuses all of the following: link-local and metadata
  (`169.254.169.254`, `100.100.100.200`, `fd00:ec2::254`, `192.0.0.192`), loopback, `0.0.0.0`, IPv4-mapped (both
  forms), 6to4 and NAT64 forms, the non-canonical numerics `2130706433`, `0x7f.1` and `127.1`, and a name that
  resolves to one public and one metadata address. `pin()` uses `CURLOPT_CONNECT_TO` with proxy bypass and no
  redirects. Private ranges are allowed by default (install policy `OUTBOUND_ALLOW_PRIVATE_ADDRESSES`), a
  documented choice for LAN panels. Multi-tenant installs must turn it off (add this to the go-live checklist).
- **WHM transport (#69, #73):**
  - every call goes through `guard->resolve()` and `pin()`. `CertificateInspector` connects to the vetted IP;
  - plain-HTTP panel ports and every port below 1024 except 443 are refused on the form and on every call;
  - TLS is verified, or pinned to an SPKI hash checked in `CURLOPT_PREREQFUNCTION`, failing closed;
  - mutating calls are form POSTs. `password`, `pass` and `token` are dropped from the request log, and only
    `metadata.output.raw` (4 KB) is logged, never `data`, so `cpsess` login URLs stay out;
  - a pin cannot be set through the form (`ServerSettings::merge` keeps the stored pin). Only the fingerprint this
    session was shown, for this exact address, can be trusted, once, and the change is audited.
- **Provisioning host:** module-log `request`, `response` and `error` pass through `Redactor` with the context
  secrets plus the new password. `ModuleQueueItem.args` is `encrypted:array`. Exception text is masked before
  `report()`. Server, service and webhook secrets are `#[Hidden]` and encrypted. `ServerRequest` and
  `GatewayRequest` keep secrets out of flashed old input.
- **Notifications (#28, #72):**
  - the template engine has no code execution and escapes HTML and Markdown output, allowing `raw` only on
    `*_html` fields. Resource limits (depth, loop iterations, output size) are in place;
  - one-time links are placed only by the system, checked against an origin allow-list (APP_URL or
    `auth_link_host`), and masked in the stored copy, and that copy is never resent;
  - previews render in `<iframe sandbox="">`, and the parent CSP blocks remote images;
  - URL settings (`support_url`, `tos_url`) use the `url` rule, which refuses `javascript:` and `data:`.
- **Host header (#59):** `trustHosts()` plus `URL::forceRootUrl(APP_URL)` outside local.
- **Install (#57):** CLI only, with no web installer route. It refuses to promote existing accounts, creates the
  first admin under a lock, and prints a generated password once (raw, never logged). It forces a password change
  and 2FA.
- **Currencies (#43):** rate sources are fixed URLs from config. Rate, conversion and review actions are sensitive
  and step-up gated.
- **Client area:** all 52 `ResolveClientContext` routes scope by `ClientContext::id()`. Bound
  `TicketAttachment` and `TicketMessage` models are checked against the ticket, and email history is scoped and
  sent-only.
- **Webhooks in:** gateway callbacks verify through `GatewayCallbackHandler`. Inbound email uses `hash_equals` over
  an HMAC-SHA256, refuses an empty secret, caps the body size and is throttled.
- **Uploads:** attachments are typed by content (`finfo`). SVG is never served inline. Downloads carry `nosniff`,
  a sandbox CSP and `attachment` disposition. Brand assets allow raster types only.
- **Headers and CSP:** `SecurityHeaders` is global, with a nonce for scripts, `object-src 'none'`,
  `frame-ancestors 'none'`, `base-uri 'self'`, per-response `form-action` for payment hand-off, HSTS on HTTPS and
  COOP. The `storage/{path}` serve and upload routes require a signature. Boost's `_boost/browser-logs` is a dev
  dependency and is registered only in local or debug.
- **Mass assignment:** models declare `#[Fillable]`. There is no `$guarded = []`, no `unguard()` and no
  `$request->all()` into models.
- **Dependencies:** `composer audit` found no advisories. `npm audit` found 0 vulnerabilities (with and without
  dev dependencies).
