# WHMCS parity study, slice B: developer architecture

Status: complete · Date read and written: 2026-10-18 · Owner: CTO

## 1. Scope, method and sources

**Scope.** How WHMCS works underneath and how third parties extend it: the External API and REST API v2, the hook
system, every module type and its function contract, cron and automation, themes, templates, email and language
systems, database and helper usage, logging, storage and security practices. Each item is compared with Mohar
(`$MOHAR_ROOT/billing`). The admin and client functional surface, release notes and community pain points are
covered by other slices and are out of scope here.

**Method.** The whole of developers.whmcs.com was enumerated from the site's own navigation data (the site is a
static documentation app whose sidebars and page bodies are published as JSON) and every page was fetched once,
sequentially, with pauses. Pages on docs.whmcs.com (automation, logs, storage, security) and the public WHMCS sample
modules on GitHub were read for the areas the developer site does not cover. Sample modules were read for interface
understanding only. Nothing here copies WHMCS text or code; descriptions are our own words. No protected source was
decoded. Appendix A lists every page with its coverage.

**Status legend.** **Built** (file cited, path relative to `billing/app` unless shown otherwise) · **Specified**
(spec section cited, `docs/product/<x>.md §n`) · **In progress** (branch in `docs/handoff/state.md`
or a worktree with commits) · **Missing** (no code, no spec). **Priority:** P0 = needed at v1 for parity or for
third-party extensibility (an event a host would hook, an API an integration or the WHMCS importer needs);
P1 = soon after v1; P2 = later or niche.

**Summary of results.** Area tables in §3–§11 hold 156 items. By status: **Built 84** (including "built in part"
and "built in kind"), **In progress 5**, **Specified 11**, **Missing 54**, not planned or not applicable 2. By priority:
**P0 68**, **P1 46**, **P2 41**. P0 items that are Missing: 10, all in two themes: no public API or client SSO
token, and driver contracts that outside packages cannot implement (§13). The 162 classic API actions are counted
separately in §11 (capability Built 122, endpoint Missing in all).

**Sources.** developers.whmcs.com in full (567 pages, Appendix A), the REST API v2 OpenAPI description, 27 pages on
docs.whmcs.com, one community thread and nine public WHMCS sample repositories (Appendix B). Mohar was read at
`develop` `b7c30d8` plus the `feature/notifications` worktree.

## 2. How WHMCS is built underneath, and the Mohar counterpart

| Concern                   | WHMCS (our words)                                                                                                                                                                                                                                                                                   | Mohar                                                                                                                                                                                                                                                                                         | Consequence                                                                                                 |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Extension unit            | A module is a folder of PHP files under `modules/<type>/<name>/`. The core discovers it by file name and calls functions named `<name>_<Function>`; only functions that exist are treated as supported. Newer types (mail, notification, widgets, metrics) use interfaces and base classes instead. | Laravel module providers under `app/Modules/<Module>` (`Support/Modules/ModuleServiceProvider.php`), discovered at boot. Drivers implement PHP interfaces and declare capabilities explicitly.                                                                                                | Capability is typed and testable in Mohar; WHMCS infers it from function existence.                         |
| Cross-cutting extension   | Global "hooks": PHP files in `includes/hooks/` plus each module's `hooks.php`, loaded on every request. A hook is a callback with an integer priority on a named point; 339 points in 19 categories. Some can veto or change data, most only observe.                                               | Domain events in `app/Events` (98 classes, scalar payloads) and registries in `app/Support` (navigation, dashboard, settings, permissions, search, themes, merge fields, client merge, automation). No veto or filter points except `Orders\PaymentGuard` and `ClientMergeRegistry` blockers. | Mohar covers observation well; it lacks a general "before" layer (§12).                                     |
| Data access by extensions | Modules and hooks read and write core tables directly through Capsule (Laravel's query builder and schema builder) and an in-process `localAPI()` that runs any API action.                                                                                                                         | Modules may only use kernel contracts, DTOs and events (ADR 0001; Pest arch tests). There is no in-process API facade.                                                                                                                                                                        | Mohar protects invariants; third parties need contracts for every read they used to do with SQL (§11, §12). |
| Remote API                | One RPC endpoint (`includes/api.php`), form POST, `action=<Name>`, 162 actions, credentials are admin-bound identifier and secret pairs with role-based action allowlists and an IP allowlist. REST API v2 (9.0+) adds a resource-style storefront and cart API with a signed state header.         | None. Only a webhook-style `/api/v1/inbound/email/{provider}` route exists (`Modules/Support/routes/api.php`).                                                                                                                                                                                | P0 gap (§11).                                                                                               |
| Scheduling                | One `cron.php` every 5 minutes; about 38 named tasks, each with its own frequency; the daily batch runs on the first call inside a configured hour. `do`/`skip`/`--force` select tasks.                                                                                                             | `automation:run` daily pipeline with ordered stages and a per-day run record (`Support/Automation/Automation.php`, `Modules/Core/Models/AutomationRun.php`), plus Laravel scheduler entries for frequent jobs.                                                                                | Mohar is idempotent per run date by contract; WHMCS relies on per-task "last run" bookkeeping.              |
| Templates                 | Smarty templates; parent and child themes (`theme.yaml`); order-form templates; per-page hooks inject template variables.                                                                                                                                                                           | Inertia + React pages; Themes module swaps design tokens only (`Support/Themes/ThemeSchema.php`).                                                                                                                                                                                             | Mohar themes cannot replace markup (by design); third-party UI needs typed slots (§12).                     |
| Configuration store       | Settings table plus `configuration.php` constants (encryption key, API access key, cron dir, hook kill switch).                                                                                                                                                                                     | `Settings` with DB override over module config defaults, registered definitions and secrets (`Support/Settings/SettingsRegistry.php`).                                                                                                                                                        | Equivalent.                                                                                                 |
| Secrets                   | A single install-wide key encrypts stored card data, passwords and module settings; API actions can encrypt and decrypt.                                                                                                                                                                            | Laravel `APP_KEY` encrypted casts (`Billing/Models/Gateway.php` `config`, `PayMethod.php` `token`, `Domains/Models/Domain.php` `epp_code`); no decrypt API.                                                                                                                                   | Better: no decrypt endpoint, tokens only for cards.                                                         |

## 7. Cron and automation

WHMCS runs one cron entry point every five minutes. Each named task has its own frequency and "last run" record;
daily tasks run on the first invocation inside the configured hour. `do` runs named tasks (forced, without moving
the schedule), `skip` excludes tasks, `--force` ignores "not due" and "already running". Tasks run in a fixed order;
the daily batch ends with a digest email to staff. Hooks fire before and after each task and at the end of the run.
Mohar: `Support/Automation/Automation.php` (stages RENEWALS 10 → HOUSEKEEPING 90), `php artisan automation:run
[--date] [--only]` (`Modules/Core/Console/Commands/RunAutomation.php`), per-task, per-date record
`Modules/Core/Models/AutomationRun.php`, heartbeat `Modules/Core/Support/AutomationStatus.php`, admin page
`Modules/Platform/Http/Controllers/Admin/AutomationController.php`.

## 11. Public API

**Current state.** Mohar has **no public API**. `ModuleServiceProvider` already mounts a module's `routes/api.php` under
`/api/v1` with the `api` middleware group (`Support/Modules/ModuleServiceProvider.php`), but the only route is the
signed inbound-email webhook (`Modules/Support/routes/api.php`). Sanctum is not installed (`composer.json`); staff API
tokens are deferred (`platform-admin.md` Deferred, §4 SHOULD); `feature-map.md §0` names an auth API that was never
specified. **Status of the API itself: Missing, P0.**

**How WHMCS does it.** The classic API is one RPC endpoint. Credentials are an identifier and secret pair bound to an
admin user; the secret is shown once; each pair carries one or more API roles, and a role is an allowlist of action
names. Requests must also come from an allowlisted IP or carry an install-wide access key. Every response has
`result` = `success|error` and a plain-text `message`; list actions page with `limitstart`/`limitnum` (default 25)
and return `totalresults`, `startnumber`, `numreturned`. The same actions run in process through `localAPI()`.
REST API v2 (WHMCS 9.0, API version 2.1.0) is separate: resource paths, HTTP status codes (202 second factor needed,
412 2FA invalid, 422 validation), a signed state header that carries the session and cart and is replaced on every
response, user and admin sessions with 2FA, admin "masquerade" sessions, and a headless checkout and invoice payment
session flow. It has 85 operations and is aimed at custom storefronts.

**Recommended shape for Mohar (our design, for the CTO).** Resource-oriented JSON under `/api/v1`, each module
owning its controllers in `routes/api.php`; tokens with abilities equal to our permission strings (`billing.invoices.view`)
so a token can never exceed its staff role; client-scoped tokens for portals; OpenAPI generated from FormRequests and
Resources; `Idempotency-Key` on every POST that moves money or provisions; cursor pagination ordered by id; ISO dates
and minor-unit money with currency; errors as RFC 9457 problem details with stable codes. Write actions call the same
Actions the admin UI uses, so behaviour cannot drift, and the same application layer replaces WHMCS's `localAPI()`.

### 12.3 Missing extension points

1. **Driver contracts in the kernel (P0).** Provisioning, registrar, fraud and inbound-email interfaces, their DTOs and
   registration live inside modules, so an outside package must import module classes, which ADR 0001 forbids. Gateways
   already show the pattern (`app/Contracts/Billing/GatewayDriver.php` + `GatewayRegistry`).
2. **Public API, tokens and client SSO tokens (P0).** See §10 and §11.
3. **Before-action filters (P1).** WHMCS lets extensions veto or rewrite: checkout and cart validation, price overrides
   and cart adjustments, tax line changes, provisioning parameter overrides and aborts, registrar pre-action aborts,
   pre-send email changes and aborts, invoice auto-cancel veto, ticket import skip, username and order-number
   generation. Mohar has two such points (`PaymentGuard`, merge blockers). Proposal: a small `Guards` registry in
   `app/Support` with typed, ordered pipelines per point (`checkout.validate`, `cart.adjust`, `provisioning.before`,
   `email.before_send`, `invoice.before_auto_cancel`), each receiving a readonly DTO and returning a typed decision.
   Better than WHMCS: a fixed, documented set of points with typed inputs and outputs instead of arbitrary arrays, and
   decisions recorded in the activity log.
4. **UI slots (P1).** Admin record pages (client, service, domain, invoice, ticket) have no place for extension panels,
   tabs, action links or fields; drivers cannot add a client-area service panel; there is no setting for head or
   footer snippets (chat widgets and analytics tags are the most common WHMCS customisation). Proposal: a `Slots`
   registry keyed by page and position that returns typed panel schemas rendered by shared React components, plus an
   admin-managed, CSP-aware snippet setting.
5. **Module registry (P1).** No runtime enable or disable, version record, metadata (name, vendor, logo, links) or
   per-role access for installed packages.
6. **Notification providers (P1).** No driver contract for chat or SMS channels and no rule engine over events.
7. **Usage metrics (P1).** No metric provider contract, metric catalogue or usage pricing.
8. **Translations (P1).** No language files, overrides or per-locale content.
9. **Report registry (P2).** No way for a package to add a report with typed columns and CSV export.
10. **Custom fields (P1).** Product custom fields exist (`Catalog/Models/ProductCustomField.php`); client, contact and
    domain custom fields and their load and save points do not. The WHMCS API passes custom fields on clients, orders
    and tickets, so the importer and API both need them.
