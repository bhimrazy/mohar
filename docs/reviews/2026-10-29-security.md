## Medium

### M1. Step-up can be brute-forced: `POST /user/confirm-password` has no rate limit

- **Where:** `billing/app/Providers/FortifyServiceProvider.php:180-185`.
  - The `booted()` block adds limiters to `password.email`, `register.store` and `password.update`. It adds none to
    `password.confirm.store`.
  - `route:list` shows that route with `web` and `auth:web` only.
- **Impact:** a stolen session (cookie theft, an unlocked shared machine) can guess the account password without limit.
  - One correct guess passes every `password.recent` gate. Those gates cover gateway secrets and certificate upload,
    server, registrar and webhook secrets, roles and staff, the client's Show password (#461), and email change
    (#393). The last one is a full account takeover.
  - The 5-per-minute login limiter is the only password brute-force defence, and this route goes around it.
- **Reproduction:** `SecretsStepUpProbesTest`, test "confirm-password is rate limited, so a hijacked session cannot
  guess its way past step-up". It sends 10 wrong guesses, then the right password, and expects 429. It gets 201 and
  the confirmation is stored. Red on SQLite and on PostgreSQL.
- **Fix:**
  1. Add a `confirm-password` limiter, about 5 per minute keyed by user id and IP, and attach it in the same
     `booted()` block.
  2. Audit failed confirmations.
  3. Consider ending the session after repeated failures.
  4. Add the route to the throttle tests (`AuthThrottleTest`).

### M2. A client login that never proved its email can be given an account, and a password reset leaves its sessions alive

- **Where:**
  - `billing/app/Modules/Platform/Actions/Clients/ManageClientLogins.php:38-61`: `invite()` attaches any existing
    non-staff `User` with that address at once. It does not check `email_verified_at` and sends no accept link. The
    login only receives an "access granted" notice.
  - `billing/app/Actions/Fortify/ResetUserPassword.php:25` saves the new password and ends no other session. The
    settings password change (`Settings/SecurityController.php:56-60`) does the same. The only callers of
    `LoginSessions::revoke()` are the install and staff-update paths. No `AuthenticateSession` middleware is set.
- **Impact:** this is the recurring class "an email address treated as proof of ownership".
  1. An attacker signs up as `accounts@corp.example` without verifying it and keeps the session.
  2. Corp asks staff to add that address to its account. Staff do, and the attacker's login gets the permissions staff
     chose (billing, support).
  3. The real owner of the mailbox uses "forgot password", signs in and verifies the address.
  4. The attacker's old session now passes `verified` and acts on Corp's invoices, credit, orders and tickets.

  The second half stands on its own as well: a stolen session survives a password reset or change (ASVS L2 V3.3).
- **Reproduction:** `ClientsLoginProbesTest`, tests C1 (attach refused for an unverified login), C2 (a reset ends the
  login's other stored sessions) and C3 (a settings password change does the same). All three are red on SQLite and
  on PostgreSQL.
- **Fix:**
  1. In `invite()`, and in owner transfer, attach an existing login only when `email_verified_at` is set. Otherwise
     send it the one-time invitation link and attach only when it is accepted. `LoginImporter::linkable()` already
     applies a verified-and-settled rule.
  2. On a password reset, call `LoginSessions::revoke($user)` and rotate the remember token. On a password change, do
     the same but keep the current session.

### M3. Fiscal PDF downloads have no rate limit; each one renders under a row lock and counts as a print

- **Where:** `billing/app/Modules/Billing/routes/web.php:100`, `:102` and `:113` (the client note, invoice and quote
  PDFs) and `:55` (the admin note PDF). The admin invoice PDF has the same gap. The work happens in
  `billing/app/Modules/Billing/Services/DocumentDownloads.php:62-79`.
- **Impact:** with Nepal VAT mode on, every download after the first does the following:
  - renders a "Copy of original — print n" with dompdf, synchronously, inside a transaction that holds
    `lockForUpdate` on the document row;
  - increments `print_count`;
  - writes a `billing.*.printed` activity row.

  Any client login with the `billing` area can loop on its own documents. That exhausts workers, adds activity rows
  without bound, contends for the invoice row lock (payments and notes take the same lock), and inflates the legal
  print counter on IRD documents. The quote PDF re-renders on every request.
- **Reproduction:** `DocumentsProbesTest`, test "a client cannot render unlimited note PDF copies". It sends 40 GETs
  and gets 40 × 200, with `print_count` at 40. Red on SQLite and on PostgreSQL.
- **Fix:**
  1. Add a named limiter (for example `billing-documents`, per user, about 10 per minute) to the client and admin
     document PDF routes.
  2. Optionally, treat a repeat download by the same user within a short window as the same print.

## Low

### L1. A mailed document is not checked against the message's client (defence in depth)

`billing/app/Modules/Notifications/Jobs/SendEmailMessage.php:113-138` and
`billing/app/Modules/Billing/Services/BillingDocumentAttachments.php:27-39` load the attached invoice, quote or note by
`related_type` and `related_id` only. Recipients come from the message's client. Nothing compares the two client ids.

- Every dispatch site today passes ids from the same row; the documents track checked all of them. So no path to
  cross-client delivery was found.
- But any future event that carries mismatched ids would mail client A's PDF, including name, address and PAN, to
  client B.

Probe: `DocumentsProbesTest`, test "the attached document belongs to the client the message is for". It builds a
message for B with A's invoice, and B's mail goes out with the invoice attached. Red on both databases.

**Fix:** pass the message's `client_id` into `BillingDocuments::document()`. Return null and log a warning when the
record belongs to another client.

### L2. Admin EPP codes go into the session without step-up

`admin/domains/{domain}/epp` (`DomainActionController.php:76-80`) needs only `domains.domains.commands`, which is not
in the sensitive tier. It returns the code through `Inertia::flash`. Sessions are stored in the database and
`SESSION_ENCRYPT` defaults to false, so the code sits in plaintext in the `sessions` table. The client EPP route has no
step-up either, while Show password now does. This predates the baseline.

**Fix:**
1. Decide whether EPP codes need step-up the way Show password does.
2. Return the code in a `no-store` JSON response, not a flash.

### L3. Product and addon provisioning secrets can be replaced without step-up

`admin/catalog/products/{product}/provisioning` and the addon equivalent accept `driver_config` secrets (through
`DriverSecrets`) under `catalog.products.manage`. That permission is not sensitive, so a `catalog.*` wildcard role can
overwrite a provisioning secret without a password confirmation. Masking on read is correct, and #457 stops a new
driver inheriting the old driver's secrets.

**Fix:** require step-up when a secret value is submitted, or make secret-bearing driver config writes sensitive.

### L4. Smaller items (no probe)

- **Cybersource lookup reads at most 3 payment rows** (`PaymentsCybersource/Drivers/CybersourceDriver.php:234`). If
  three declines sorted above an unread capture, the lookup would classify the attempt as failed. With `id:desc` and
  one session per reference this looks unreachable. **Fix:** answer "ambiguous" when the provider returns more rows
  than were read.
- **Razorpay webhooks carry no signed timestamp**, so they have no replay window. This is safe by structure: a link
  event only triggers a `lookup()` of the stored link, and refund events re-fetch the refund from the API and are
  idempotent on the refund id. Document it in the driver.
- **`AcceptServerValues` (#463)** copies the domain the server reports into `services.domain` without validating it.
  Staff review the value and output is escaped. **Fix:** check it with `DomainGuard::isValidName`.
- **The checkout and sign-up forms say "An account with this email already exists".** Someone can use this to check
  which addresses have accounts; the `orders-checkout` and `register` limiters slow it down. Accept this or reword
  the message.
- **Dependencies:**
  - `composer audit` reports CVE-2026-45070 in `symfony/mime` v8.1.7 (header injection through non-token characters in
    MIME parameter names), reported 2026-10-28. Our attachment file names are system-generated (`invoice-<n>.pdf`), so
    we found no attacker-controlled path. Bump once the fix release is past the 7-day cooldown.
  - `docs-site` still has the build-time `postcss-selector-parser` moderate advisory (baseline L2).
  - `npm audit` in `billing/` is clean.

## Verified secure

- **Hosted payments settle only through `lookup()`.**
  - Drivers receive `PaymentAttemptRef` built from stored fields only. `ReturnHint` only picks which attempt to look up.
    A signed "paid" return (eSewa, Cybersource ACCEPT, Razorpay paid) is kept as evidence and at most sends the attempt
    to review.
  - Settle guards in `SettlePaymentAttempt` send the attempt to review when the txn id, currency or amount is missing
    or does not match, and when the txn id was already used. These checks run under `lockForUpdate`. They are backed by
    unique indexes on `(gateway, provider_txn_id)` for attempts and `(gateway, gateway_txn_id)` for transactions, and
    `(gateway, provider_ref)` is now unique too.
  - Each new driver checks the provider's answer against the stored attempt:
    - connectIPS: a strict echo of txn, merchant, app and amount;
    - Razorpay: `linkBelongs` and a payment↔link check;
    - Cybersource: a reference filter on the rows it reads.
- **Signatures are checked before persistence, in constant time.**
  - Stripe uses `hash_equals` over every v1 candidate, with a tolerance window.
  - Razorpay checks the HMAC over the raw body before parsing.
  - Cybersource checks the exact signed field set, then `hash_equals`, then the access key and profile, within a
    5-minute window.
  - An empty secret fails closed.
  - Rejections log only the IP, the body length and its sha256.
- **The signed cancel hint (#500)** counts only with a valid signature and a return that names the attempt. It only
  informs the next lookup and never settles anything by itself.
- **Refunds.**
  - Stripe pending refunds settle only when payment, amount and currency match. Released ids are matched under lock,
    and race probes run on PostgreSQL.
  - Account-credit refunds need `billing.credit.refund` (sensitive tier) and `password.recent`. The gateway variant also
    needs `billing.refunds.manage`. The payment must belong to the client, the amount is capped by
    `refundable_remaining` under lock, and the ledger balance is checked under the client lock.
  - The #474 portal-refund re-lookup only flags rows, is capped and indexed, and takes its locks in a fixed order.
- **SSRF.** Gateway hosts are fixed in config with an https check. Overrides work only in local and testing. Staff have
  no URL setting.
- **Rate limits on payment routes.** Gateway return: 60 per minute, with at most one lookup per attempt per minute.
  Webhooks: 120 per minute. Client pay, continue and close: `billing-pay`. Resume and close are scoped by client and
  invoice.
- **Certificates (#489).**
  - The `.pfx` is read in memory, capped at 64 KB, and never written to disk, so its file name cannot cause traversal.
    There is no download route.
  - Refusals use fixed text, never OpenSSL error output.
  - The passphrase and key are `SensitiveParameter`, the bundle redacts itself in `__debugInfo`, and serialising it
    throws.
  - The PEM is stored only in `gateways.config` (`encrypted:array`, hidden). Inertia props carry only the summary.
  - `certificates.*` is kept out of old input, and the log backstop masks the PEM by value.
  - The audit entry records only "rotated" and the expiry dates.
- **Sensitive tier.** `Role::allows()` grants a sensitive permission only to the exact key or `*`, so a `billing.*` role
  gets 403 on the gateway edit, update and test routes. Every secret-bearing admin write has `password.recent`.
- **Client Show password (#461).** It is scoped by `ClientContext`, so another client's service returns 404. It needs
  step-up, counts reveals atomically against a per-login limit, is audited, and answers `no-store`. Staff impersonating
  a client cannot step up.
- **Passwordless accounts and email change.**
  - A login with no password, or with an expired one-time password, is never "recently confirmed".
  - Email change needs step-up, clears `email_verified_at`, and notifies the old address.
  - Install runs from the CLI only.
- **Document attachments (#504).**
  - The queued job carries only the message id and is encrypted.
  - The document is re-derived at send time from a closed type set (`tax_note`, `invoice`, `quote`), drafts excluded,
    and only for templates that attach one.
  - Resends keep the original recipient, and there is no free-address input.
  - Note resend needs `billing.tax_notes.resend`, a per-user throttle, and an audit entry.
- **Client-area documents.** Note, invoice and quote PDFs are scoped through `ClientContext` plus the `billing` area.
  Another client's note returns 404, and an existing test pins it.
- **VAT registers and buyer PANs.**
  - The export needs a sensitive export permission, which `reports.*` does not grant, plus `password.recent` and a
    throttle. Each export writes one `report.exported` audit entry with its filters.
  - CSV formula injection is closed by `SafeCsv`. A probe put `=`, `+`, `-`, `@`, tab, CR and leading-space payloads
    into the buyer company, the PAN, the line description and the seller name. Every cell came back neutralised on
    both databases (probe deleted).
  - The `tax_note` webhook payload carries no PAN or address.
- **PDF engine.** dompdf 3.1.6 runs on its defaults: remote loading and PHP off, chroot at `base_path()`. Every raw
  output in the PDF views wraps `e()`. The billing PDFs load no images. The From and Bill-to blocks are closed field
  sets.
- **Store, cart and checkout (#478).**
  - Everything is re-priced on the server from ids only.
  - Cart items are looked up only inside the shopper's own cart.
  - `CustomerResolver` accepts only accounts the login owns or holds `billing` on.
  - Signed-in shoppers always buy in the account currency.
  - Checkout registration always creates a new client and never attaches to an existing one by email.
  - `.np` registration is blocked in pricing, in the cart, and in `CreatePendingDomain` (which covers staff orders).
- **KYC.** Uploads are re-encoded with GD, encrypted, and stored under random paths on a private disk. Staff images need
  signed URLs and sensitive permissions. Orphan files are deleted only by staff, after step-up, bound by a digest, and
  re-checked under the client lock.
- **Server import.** It needs a sensitive permission, step-up and a throttle. Accepted values are limited to domain,
  IP and status, bound by a digest and re-read under row locks. Email matches carry the unverified and recently-changed
  flags.
- **Support merge key rotation (#450).** An old key opens only the "merged" page, which shows the ticket number and
  nothing else.
- **Workflows.**
  - There is no `pull_request_target`.
  - Top-level `permissions: contents: read` everywhere.
  - Label-triggered jobs (`ci`, `deploy-smoke`, `load-test`) run only for their own label. Applying a label needs
    triage rights.
  - Fork PRs receive no secrets. `GITHUB_TOKEN` with `packages: write` or `contents: write` exists only in the
    `workflow_dispatch` image build.
  - `github.head_ref` reaches `run:` only through `env`.
