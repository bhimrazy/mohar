threads on #28, #58, #62, #65, #69, #72 and #73. Question from the owner: how to get more throughput with

## 2. Quality

What the second and third rounds found, by PR:

- #28: security B1 (secret-carrying links taking their host from the request) took four security passes;
  each fix closed the reported path and left another. The same class returned in #72 round 1 (invitation
  fallback bypassed the secret policy) and was fixed by moving the check to one choke point
  (`AccountLinks::problem()`).
- #69: round 1 security found the cPanel account takeover (adopting a root-owned account by name); the
  board's re-check found the fix gave each renamed attempt a fresh deadline.
- #73: round 1 found `settle()` applying a stale answer outside the lock; the fix gated "Create again" at
  click time only, found in security round 2; round 3 was clean.
- #62, #65, #72: the re-check found an issue introduced by the fixes (same pattern as #6, #7, #8, #10 in wave 1).

Recurring defect classes, in order of frequency: a policy enforced at each call site instead of one choke
point (secret links, brand name via `config('app.name')`); check-then-act outside the lock or a gate that
is not single-use (#69, #73, every money module in wave 1); identity by name instead of proof (#69);
fixes that regress (6 PRs); PR text claiming what the code does not do (wave 1, less since the fixes table).

Conclusion for the owner's question: the later rounds are not redundant. Roughly half of what they catch is
caused by the fix round itself. Dropping them trades one to two hours per PR for escaped auth and money bugs.

Test and CI health: 2,445 Pest tests, growing about 150 per feature PR. Reviewers write probe tests and
delete them ("throwaway Pest tests, deleted afterwards"); the re-reviewer rewrites them. #72 kept its probes
(`MailReviewFixesTest`), which is the better practice. CI's PostgreSQL step takes 550 s against 154 s for
the same suite on SQLite; the next 20 s of growth hits `timeout-minutes: 15`. Issue #24 (bring CI back to
2–3 min) has gone the other way.

## 3. Process

Gates that earn their cost: the review board (found most money and authorisation bugs), the security
reviewer on auth/money/secrets (the takeover and the link bypass), the re-check after fixes that touch locks,
transactions or gates, the database reviewer on migrations, the architect reviewing the brief before the
build (#61/#62 went through in under 3 h each), the `ci` label on drafts, and the fixes table in the PR body.

Gates that do not: `qa-design-reviewer` (overlaps `product-reviewer`, slowest role, already marked as
such); a re-review round when round 1 had no blocking or medium item; the CTO's local full-suite run at
merge after CI has run the same commit; a `product-reviewer` pass per PR instead of per wave.

CTO decisions that cost time: the 3,000-line cap was overridden twice today (#69, #72) and #28 was allowed
to reach 14.8k lines and seven review passes; six workstreams are in flight on a box the operating model
limits to two engineers; the periodic review round (four Opus/Fable agents) was launched at peak load;
Stripe was built before the simulator that could test it. Good calls: splitting cPanel into 1a–3, the
`ci` label, ADR 0016, the one-fix-list-per-PR rule, PostgreSQL in every verdict.

Concurrency against the limits: `heavy.sh` caps heavy commands at three, but not agents, dev servers,
seeds or Playwright; the practical limit is around two engineers plus two reviewers. Beyond that every
agent gets slower and reviews start on heads that are still moving.

## 4. Debt and risks for the next month

- CI time and test memory: 2 → 13 min in two days, with a 15-min timeout and a 1 GB worker limit. This
  blocks merges before anything else does.
- Review-only enforcement: branch protection is unverifiable (403) and all agents share one account, so
  the gates hold only by discipline. Any agent can push to `develop`.
- 40 open issues, 7 of them "follow-ups from PR #n review" with no owner or date; they accumulate silently.
- Stacked branches (1b on 1a on B2) multiply `develop` merges and block CI while conflicted.
- Nothing has run outside the codespace yet; #79 (FrankenPHP image) is the first attempt. Key rotation
  (#25) and the 10-22 framework bump (#11, held-back security fixes) are due.
- Work under `/tmp` (a full `billing` copy at the scratchpad) and local-only review helpers are lost on reboot.

## 5. Recommended changes

1. **Reviewer probes become committed tests.** The reviewer posts each probe as code in the review; the
   engineer commits them as failing tests before fixing, and the fixes table cites them. Re-review becomes
   "probes green in CI plus a diff read of the fix", 10 min instead of a 30–60 min Opus agent, and the
   fix-regression class is caught by the suite. Expected: one fewer round on most PRs, and no #28-style
   four-pass bypass hunts.
2. **CI is the only full-suite runner; bring it to 6 min.** Local gate: pint, Larastan, tsc, `vp check`,
   Vitest, the module's tests and `tests/Arch`. Full SQLite and PostgreSQL suites run in CI only; the CTO
   merge step drops its local suite run. Fix the PostgreSQL step first (550 s: seed once into a template
   database, check the worker count). Add `--no-deps` to `new-worktree.sh` for docs and review worktrees.
   Expected: three to four fewer full-suite runs per PR on the box, load under the core count, and the
   headroom any extra agent needs.
3. **Scale engineers by location, not count.** Local: at most two engineers and two reviewers at once.
   Further engineers run remote (`isolation: "remote"`) on workstreams with no shared-kernel change, with CI
   as their gate; the CTO merges locally. Verify availability with one pilot this week (Stripe saved methods
   or the `.np` registrar) and compare lead time and review findings with a local run. This is the only form
   of "more parallel agents" the machine can absorb; its cost is the owner's call.
4. **Hard PR cap: 1,500 lines for drivers, money and security; 3,000 otherwise; no overrides.** The split
   plan goes in the brief, as cPanel 1a–3 did. Expected: one to two review passes and 1–2 h in-session lead
   time, which the data in §1 already shows for PRs under 2k lines.
5. **Trim the gate table, keep the ones that found the bugs.** Drop `qa-design-reviewer`; `re-reviewer`
   only when round 1 had a blocking or medium item, or the fix touched a lock, transaction or gate; the
   architect reviews the brief and skips the finished kernel PR when the diff matches it; security
   re-check stays mandatory for auth, money, secrets and locks; product sweep once per wave. Docs-only PRs,
   including these review files, merge on CI alone.

Not recommended: fewer review rounds in exchange for more engineers (§2), or more local agents without
changes 2 and 3 (§3). The largest single gain available is work that runs while the session is off,
which is a scheduling and cost decision for the owner, not a process change.
